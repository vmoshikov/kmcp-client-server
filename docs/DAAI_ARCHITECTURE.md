# Архитектура DAAI System

## Обзор системы

DAAI (Data Analysis and Agent Interface) - это мастер-сервис, который координирует анализ Kubernetes кластеров через MCP Server с использованием kagent tools.

## Компоненты системы

### 1. DAAI (Master Service)

**Роль:** Центральный сервис, координирующий все операции

**Функции:**
- Прием HTTP запросов от пользователей через эндпоинты (`agent_action_1`, `agent_action_2`, ...)
- Авторизация и аутентификация пользователей
- Валидация и обработка входящих запросов
- Бизнес-логика обработки запросов к агентам
- Логирование всех операций
- Координация взаимодействия с другими сервисами

**Эндпоинты:**
- `POST /agent_action_1` - первое действие агента
- `POST /agent_action_2` - второе действие агента
- `POST /agent_action_N` - дополнительные действия агента

### 2. MCP Client (внутри DAAI)

**Роль:** Клиент для взаимодействия с MCP Server

**Функции:**
- Подключение к MCP Server в Parent Cluster
- Формирование запросов в формате MCP Protocol
- Вызов одного или нескольких tools
- Обработка ответов от MCP Server

**Реализация:** Использует реализацию из `mcp/client.go`

### 3. KaaS (Kubernetes as a Service)

**Роль:** Сервис управления кластерами

**Функции:**
- Хранение информации о кластерах (Parent и Children)
- Предоставление информации о кластерах по запросу
- Управление конфигурациями кластеров (kubeconfig, endpoints, credentials)

**Интерфейс:** REST API или gRPC

**Данные, предоставляемые DAAI:**
- `clusterType` - тип кластера (Parent/Child)
- `kubeconfig` - конфигурация для подключения к кластеру
- `endpoint` - endpoint кластера
- `credentials` - учетные данные для доступа

### 4. MCP Server (kmcp) в Parent Cluster

**Роль:** Сервер, запускающий kagent tools

**Расположение:** Parent Cluster Kubernetes

**Функции:**
- Прием запросов от MCP Client
- Запуск указанных kagent tools
- Координация выполнения tools
- Возврат результатов выполнения

### 5. kagent tools

**Роль:** Инструменты для анализа Kubernetes кластеров

**Источник:** [kagent-dev/tools](https://github.com/kagent-dev/tools)

**Примеры tools:**
- `kubectl_get_pods` - получение списка подов
- `kubectl_get_nodes` - получение списка нод
- `get_events` - получение событий кластера
- Другие инструменты для анализа

**Функции:**
- Анализ состояния Parent Cluster
- Анализ состояния отдельных Children Clusters
- Выполнение kubectl команд
- Взаимодействие с Kubernetes API

### 6. Parent Cluster Kubernetes

**Роль:** Основной Kubernetes кластер

**Характеристики:**
- Содержит множество Children Clusters
- Внутри него развернут MCP Server (kmcp)
- Является точкой входа для анализа дочерних кластеров

### 7. Children Clusters Kubernetes

**Роль:** Дочерние Kubernetes кластеры

**Характеристики:**
- Множество независимых кластеров
- Управляются через Parent Cluster
- Могут анализироваться индивидуально через kagent tools

### 8. Postgres (Pangolin)

**Роль:** База данных для логирования метаданных

**Хранимые данные:**
- Метаданные запросов
- Временные метки
- Идентификаторы запросов и пользователей
- Результаты операций

### 9. Clickhouse

**Роль:** База данных для аналитики и метрик

**Хранимые данные:**
- Метрики производительности
- События системы
- Аналитические данные
- Долгосрочное хранение для отчетности

### 10. IDP (RAG - Retrieval-Augmented Generation)

**Роль:** Система поиска релевантной документации для обогащения контекста

**Функции:**
- Векторный поиск в базе документации
- Поиск релевантных примеров и best practices
- Извлечение контекста на основе результатов анализа
- Подготовка контекста для LLM обработки

**Использование:**
- Получает результаты анализа от DAAI
- Выполняет семантический поиск в документации
- Возвращает релевантные фрагменты документации
- Предоставляет контекст для улучшения ответа LLM

### 11. GigaChat LLM

**Роль:** Большая языковая модель для обработки и анализа результатов

**Функции:**
- Анализ результатов выполнения kagent tools
- Генерация структурированных ответов с учетом контекста
- Формулирование рекомендаций на основе анализа
- Интерпретация технических данных в понятный формат

**Использование:**
- Получает результаты анализа и контекст из IDP
- Обрабатывает данные через LLM API
- Генерирует анализ, рекомендации и выводы
- Возвращает обогащенный ответ для пользователя

## Поток данных

### 1. Инициализация запроса

Пользователь отправляет HTTP POST запрос на один из эндпоинтов DAAI:
```json
{
  "clusterId": "cluster-123",
  "action": "analyze",
  "params": {
    "namespace": "default",
    "toolNames": ["kubectl_get_pods"]
  }
}
```

### 2. Логирование

DAAI немедленно логирует запрос:
- **Postgres (Pangolin):** Метаданные, временные метки, идентификаторы
- **Clickhouse:** Метрики, события для аналитики

### 3. Бизнес-логика DAAI

- **Авторизация:** Проверка прав доступа пользователя
- **Валидация:** Проверка корректности запроса
- **Обработка:** Применение бизнес-правил, трансформация данных

### 4. Получение информации о кластере

DAAI обращается к KaaS для получения информации о кластере:
- REST/gRPC запрос с `clusterId`
- KaaS определяет тип кластера (Parent/Child)
- KaaS возвращает конфигурацию кластера (kubeconfig, endpoint, credentials)

### 5. Формирование MCP запроса

DAAI использует MCP Client для формирования запроса:
- Создается MCP Client с URL MCP Server в Parent Cluster
- Формируется MCP запрос с указанием tools и параметров
- Информация о кластере включается в параметры

### 6. Вызов MCP Server

MCP Client отправляет запрос к MCP Server (kmcp) в Parent Cluster:
```json
{
  "method": "tools/call",
  "params": {
    "name": "kubectl_get_pods",
    "arguments": {
      "namespace": "default",
      "kubeconfig": "...",
      "clusterType": "child"
    }
  }
}
```

### 7. Выполнение kagent tools

MCP Server запускает указанные kagent tools:
- Tools получают параметры, включая информацию о кластере
- Tools определяют, какой кластер анализировать (Parent или Child)
- Tools выполняют анализ через kubectl или Kubernetes API

### 8. Анализ кластера

**Для Parent Cluster:**
- Tools подключаются к Parent Cluster через kubeconfig
- Выполняются команды kubectl или API запросы
- Анализируется состояние Parent Cluster

**Для Children Cluster:**
- Tools переключают контекст на Children Cluster
- Выполняются команды kubectl или API запросы с указанием контекста
- Анализируется состояние конкретного Children Cluster

### 9. Возврат результатов

Результаты проходят обратный путь:
1. kagent tools → MCP Server (результаты анализа)
2. MCP Server → MCP Client (MCP Response)
3. MCP Client → DAAI (обработанные результаты)
4. DAAI → Пользователь (финальный HTTP ответ)

### 10. Получение контекста из документации (IDP RAG)

DAAI обращается к IDP для получения релевантного контекста:
- Формируется запрос на основе результатов анализа, `clusterId` и `toolNames`
- IDP выполняет векторный поиск в базе документации
- IDP возвращает релевантные фрагменты документации, примеры и best practices
- Контекст используется для обогащения ответа

**Формат запроса к IDP:**
```json
{
  "query": "результаты анализа кластера",
  "clusterId": "cluster-123",
  "toolNames": ["kubectl_get_pods", "kubectl_get_nodes"],
  "results": {...}
}
```

**Формат ответа от IDP:**
```json
{
  "relevantDocs": [
    {
      "title": "Troubleshooting Pod Issues",
      "content": "...",
      "relevance": 0.95
    }
  ],
  "context": "Сводка релевантной информации из документации"
}
```

### 11. Обработка через LLM GigaChat

DAAI отправляет данные в GigaChat для обработки:
- Формируется промпт с результатами анализа и контекстом из IDP
- GigaChat анализирует данные с учетом документации
- Генерируется структурированный ответ с анализом и рекомендациями
- Ответ обогащается интерпретацией технических данных

**Формат запроса к GigaChat:**
```json
{
  "results": {...},
  "context": "контекст из IDP",
  "prompt": "Проанализируй результаты анализа кластера и предоставь рекомендации"
}
```

**Формат ответа от GigaChat:**
```json
{
  "analysis": "Детальный анализ состояния кластера...",
  "recommendations": [
    "Рекомендация 1",
    "Рекомендация 2"
  ],
  "summary": "Краткое резюме"
}
```

### 12. Финальная обработка и формирование ответа

DAAI:
- Обрабатывает и агрегирует результаты от всех tools
- Получает контекст из IDP (RAG)
- Обрабатывает данные через GigaChat LLM
- Логирует результаты в Postgres и Clickhouse
- Формирует финальный обогащенный ответ пользователю

**Формат финального ответа:**
```json
{
  "status": "success",
  "clusterId": "cluster-123",
  "results": {...},
  "analysis": "Анализ от GigaChat",
  "recommendations": [...],
  "context": "Контекст из документации"
}
```

## Особенности реализации

### Обработка ошибок

- **Ошибки авторизации:** HTTP 401
- **Ошибки валидации:** HTTP 400
- **Ошибки KaaS:** HTTP 404 (кластер не найден)
- **Ошибки MCP Server:** HTTP 500
- **Ошибки выполнения tools:** Включаются в результаты с пометкой `error`
- **Ошибки IDP (RAG):** Fallback на базовый контекст, ответ формируется без обогащения
- **Ошибки GigaChat LLM:** Fallback на прямую передачу результатов без LLM обработки

### Масштабирование

- **DAAI:** Stateless сервис, можно горизонтально масштабировать
- **MCP Server:** Может быть развернут в нескольких репликах
- **KaaS:** Может использовать кэширование для часто запрашиваемых данных

### Безопасность

- Авторизация на уровне DAAI
- Передача credentials через защищенные каналы
- Валидация всех входных данных
- Логирование всех операций для аудита

## Интеграция компонентов

### DAAI ↔ KaaS

**Протокол:** REST или gRPC

**Запрос:**
```json
{
  "clusterId": "cluster-123"
}
```

**Ответ:**
```json
{
  "clusterType": "child",
  "kubeconfig": "...",
  "endpoint": "https://child-cluster.example.com",
  "credentials": {
    "token": "..."
  }
}
```

### DAAI ↔ MCP Server

**Протокол:** MCP Protocol over HTTP

**Запрос:** См. формат в `mcp/client.go`

**Ответ:** Результаты выполнения tools

### MCP Server ↔ kagent tools

**Протокол:** Внутренний вызов tools

**Параметры:** Передаются через MCP Protocol

**Результаты:** Возвращаются в формате MCP Response

### DAAI ↔ IDP (RAG)

**Протокол:** REST API

**Запрос:**
```json
{
  "query": "результаты анализа",
  "clusterId": "cluster-123",
  "toolNames": ["kubectl_get_pods"],
  "results": {...}
}
```

**Ответ:**
```json
{
  "relevantDocs": [...],
  "context": "релевантный контекст из документации"
}
```

### DAAI ↔ GigaChat LLM

**Протокол:** REST API (GigaChat API)

**Запрос:**
```json
{
  "model": "GigaChat",
  "messages": [
    {
      "role": "system",
      "content": "Ты эксперт по Kubernetes..."
    },
    {
      "role": "user",
      "content": "Проанализируй результаты: {...}"
    }
  ],
  "context": "контекст из IDP"
}
```

**Ответ:**
```json
{
  "analysis": "...",
  "recommendations": [...],
  "summary": "..."
}
```

## Мониторинг и логирование

### Метрики в Clickhouse

- Время выполнения запросов
- Количество успешных/неуспешных операций
- Использование ресурсов
- Производительность tools

### Логи в Postgres (Pangolin)

- Все HTTP запросы
- Результаты авторизации
- Информация о кластерах
- Ошибки выполнения

## Будущие улучшения

1. **Кэширование результатов** от KaaS и IDP
2. **Параллельное выполнение** нескольких tools
3. **Retry механизм** для временных ошибок
4. **Circuit breaker** для защиты от недоступности сервисов
5. **Метрики Prometheus** для мониторинга
6. **Distributed tracing** для отслеживания запросов
7. **Улучшение RAG** - более точный поиск релевантной документации
8. **Fine-tuning GigaChat** - адаптация модели под специфику Kubernetes
9. **Streaming ответов** от GigaChat для real-time обновлений
10. **Мультимодальность** - обработка не только текстовых, но и графических данных
